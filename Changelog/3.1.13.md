## MacStroke 3.1.13

**新增 / Added**

- Wheel gestures now act on the window under the pointer instead of the frontmost app. Hover a background window, hold the trigger button and scroll: that window scrolls, the front app stays put, and focus never moves. This is how macOS already routes a real scroll wheel (System Settings → Accessibility → "Scroll inactive windows"), so nothing is stolen from the front app

  滚轮手势现在打的是**光标下那扇窗**，不再是前台那一家。把指针停在后台窗口上，按住触发键滚一下：滚的是那扇窗，前台不动，焦点也不跳。macOS 自己就是这么派发真实滚轮的（系统设置 → 辅助功能里的「滚动不活跃窗口」），所以前台什么都不会被抢走

- Matching follows the same rule: the wheel notch picks the rules of the app under the pointer, so an app-specific binding (for example Rex's Shift+wheel horizontal scroll) now fires when the pointer rests on that app's background window

  规则匹配跟着同一条口径：滚轮按指针下那家的规则挑，所以 App 专用绑定（比如 Rex 的 Shift+滚轮横向滚动）在指针停在那家后台窗口上时也能命中

- There is no switch for this: the behaviour is the default, and the transparent gesture canvas already lets the hit test pass straight through to the window beneath it

  这一项没有开关：行为就是默认值。手势画布本来就是「忽略鼠标事件」的透明层，命中测试会直接穿透它

**修复 / Fixed**

- Keyboard actions keep going to the active app. A shortcut fired by a wheel notch (⌘⇧[ to change tabs, say) still lands in the front app, because injected keys only reach the active application — so the rule lookup falls back to the front app for those

  键盘动作仍然打给活跃 App。滚轮触发出来的快捷键（比如 ⌘⇧[ 切标签页）还是落在前台，因为注入的按键只进活跃应用 —— 这类动作的规则匹配因此退回前台

- Pointing at an app that is on the black list no longer swallows a keyboard action. Only actions that actually land where the pointer is (wheel, side-button replay, coordinate clicks) are suppressed there; before this, "hold trigger and change tab" could silently do nothing whenever the pointer happened to rest on a blocked window

  指针停在被黑名单排除的 App 上时，不再把键盘动作一起吞掉。只有真正按指针落地的动作（滚轮、侧键回放、坐标点击）才在那里被拦下；在此之前，只要指针恰好压在一个被排除的窗口上，「按住触发键切标签页」就可能悄悄什么都不做

- A gesture that only started because of the window under the pointer is handed straight back on release: it is never matched against the front app's stroke rules and never turned into a synthetic context-menu click. This keeps a blacklisted or rule-less front app untouched, exactly as before

  只因「指针下那家」才起手的那一笔，抬手时原样交回：不拿前台那家的轨迹规则去匹配，也不会被合成一次右键菜单点击。黑名单里、或压根没配规则的前台 App 因此和以前一样不受影响

**注意 / Notes**

- Drawing a stroke still matches the front app and still moves focus when the action needs it — that path injects keystrokes, and keystrokes only reach the active app. Only the wheel path gained pointer attribution

  画轨迹那条路仍然按前台匹配、需要时也仍然挪焦点 —— 那条路投的是按键，而按键只进活跃应用。这一版只有滚轮那条路拿到了指针归属

- Window lookup uses a real hit test (`NSWindow.windowNumber(at:belowWindowWithWindowNumber:)`) and reads a single window's owner afterwards, so it needs the Accessibility permission only — not Screen Recording

  取窗口用的是真实命中测试，之后再单独查那一扇窗的归属，所以只需要辅助功能授权，不需要「屏幕录制」
